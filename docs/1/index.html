    Einleitung

    Motivation

    In der zweijährigen Assistentenausbildung für Informationsverarbeitung – Technik muss ein vierwöchiges Praktikum nachgewiesen werden, um die Ausbildung abzuschließen. Alternativ darf während der gesamten Ausbildungszeit an einer AG teilgenommen werden, um dasselbe Ergebnis zu erzielen wie durch ein Praktikum.
    Zur Auswahl standen die Game-Design-AG und die Maker-AG. Da die Maker-AG interessant aussah und ich somit kein Praktikum absolvieren müsste, habe ich mich für die Maker-AG eingeschrieben.

    Nun, ein Jahr später, hat unser Lehrer der AG, Herr Keller, gesagt, dass jeder Schüler, der die Maker-AG als Praktikumsalternative nutzen will, ein Projekt abschließen muss, das der AG langfristig helfen wird. Gesagt, getan...
    Die Idee für ein Organisations- und Sortiersystem hatte ich schon etwas länger, wusste aber noch nicht genau, wie ich sie umsetzen würde. Nach weiterer Überlegung und Rücksprache mit dem Lehrer ist schließlich dieses Projekt entstanden. Das ganze Projekt hat mich noch einmal herausgefordert, alles anzuwenden, was ich in der Assistentenausbildung gelernt habe, was sehr viel Spaß gemacht hat.

    Ziel

    Das Ziel des Projektes ist es, ein System zu entwickeln, welches die Gegenstände in den Schränken im Raum U24, U25 und des Hardware-Raumes sortiert und organisiert. Dies wird durch die Erstellung einer Datenbank erfolgen, welche die Informationen zu den Gegenständen speichert, wie Anzahl, Modell/Marke, Standort (Schrank/Raum/Regal) etc. Außerdem wird jeder Gegenstand eine eigene kleine Dokumentation bekommen, welche noch einmal im Detail den Gegenstand beschreibt und Weiteres.

    Anmerkung

    Da es zu der Eintragung der ganzen Gegenstände in die Datenbank wenig zu sagen gibt, wird dieser Teil hier eher weniger erwähnt, jedoch wird vieles noch einmal in den einzelnen Dokumentationen der Gegenstände erwähnt werden.

    Ich habe mir für dieses Projekt bei vielen Dingen viel Mühe gegeben, um es zu perfektionieren, und würde es schätzen, wenn dieses Projekt auch in Zukunft weiter existiert und genutzt wird.

    Ausgangssituation

    Das Projekt ging durch viele Überarbeitungen. Eine davon war die Auswahl der Datenbank, welche genutzt werden würde, um alle Daten der Gegenstände zu speichern. Herr Keller schlug mir MongoDB vor, wovon ich davor noch nicht gehört hatte. MongoDB wäre in diesem Fall sogar etwas besser gewesen, da man es einfacher hätte integrieren können. Ein Problem war jedoch die Installation. Da der Raspberry Pi ein ARM64-Produkt ist und MongoDB hauptsächlich auf x86-64 läuft, waren die wenigen Versionen, die für ARM erstellt wurden, entweder veraltet, inkompatibel oder einfach instabil. Das war etwas frustrierend, und nach einiger Zeit habe ich aufgegeben und stattdessen MariaDB installiert, welches auf SQL basiert.

    Design

    Der Prozess läuft so ab, dass, sobald ein Nutzer die Website aufruft, ein Request an den Server gesendet wird, um alle HTML-Seiten zu bekommen. Diese HTML-Seiten verlinken zu den JavaScript- und CSS-Dateien, welche ebenfalls angefragt werden. In den JavaScript-Dateien ist eine Verlinkung zu einer PHP-Datei, welche dann auch auf die Seite geladen wird. In der PHP-Datei befindet sich Code, welcher eine Verbindung mit einer MariaDB-Datenbank auf dem Raspberry Pi herstellt und von dort die gewünschten Daten abruft.

    • categories.parent_id (Self-Reference) zeigt auf eine andere Zeile in derselben Tabelle. Damit lassen sich Kategorien beliebig tief verschachteln, z.B. Hardware → Computer → Laptop. NULL bedeutet: oberste Ebene, kein Elternteil.
    • specs (Key-Value) statt für jeden möglichen Spec eine eigene Spalte in items anzulegen, speichert diese Tabelle beliebige Eigenschaften als Schlüssel-Wert-Paare. Ein Laptop bekommt "Prozessor / i5", ein Hammer bekommt "Gewicht / 800g", ohne dass die Datenbankstruktur geändert werden muss.
    • item_tags (Pivot-Tabelle) verbindet Items und tags in einer Viele-zu-Viele-Beziehung. Ein Item kann mehrere Tags haben, ein Tag kann mehreren Items zugewiesen sein. Die Tabelle selbst hat keine eigenen Daten, nur die zwei Fremdschlüssel.
    • changelog protokolliert jede Änderung an einem Item. Welches Feld wurde geändert, von welchem Wert, auf welchen Wert, wann und von wem. Damit lässt sich der komplette Verlauf eines Eintrags nachvollziehen.
    • feedback ist eine sehr simpel gehaltene Tabelle welche nur Name Problem (also Nachricht) und halt den Timestamp anzeigt. Das einzige anzumerkende ist, dass es extra so simpel gehalten ist, da ich keine Lust hatte ein Benutzersystem zu erstellen (welches auch noch mehr Probleme mit sich bringt).

    Administration

    Die Administration dieser Website wurde auf eine sehr besondere Weise gelöst. Mir war klar, dass ich entweder einfach eine Administrationsseite erstellen könnte oder phpMyAdmin erreichbar machen könnte, aber diese beiden Optionen verfügen über keine HTTPS-Verschlüsselung. Obwohl wir uns nur im Schulnetz befinden, sollte man trotzdem auf Sicherheit achten. Deshalb habe ich mir etwas anderes überlegt.

    Ich habe einmal einen Service bei mir zu Hause laufen lassen (für die, die es kennen: n8n), welcher einen besonderen Weg hatte, darauf zuzugreifen. Wenn man ihn in einem Docker-Container betreibt, kann man über einen SSH-Proxy darauf zugreifen. Genau so habe ich es hier gemacht.

    Zuerst habe ich eine Seite in Apache2 erstellt, welche nur vom lokalen Gerät aus aufrufbar ist. Das heißt, dass niemand auf die Seite zugreifen kann, wenn man nicht direkt von diesem Gerät darauf zugreift.

    SSH hat eine Option, um einen Proxy mit dem Server aufzubauen. Man setzt dann die Adresse des Servers auf einen lokalen Port, z. B. 8080. Das heißt, sobald man eine Proxy-Verbindung mit dem Server herstellt, kann man auf dem eigenen Rechner im Browser localhost:8080 aufrufen, und diese Verbindung wird weitergeleitet zum Server, welcher dann die Website anzeigt.

    Eine solche Option ermöglicht es, dass der komplette Traffic der Administrationsseite über den SSH-Proxy läuft, also eine verschlüsselte Verbindung besteht.

    Die Website selbst soll dann ermöglichen, Dateien hinzuzufügen oder zu bearbeiten bzw. zu löschen.

    Eine große Hilfe während der Entwicklungszeit war der Zugriff auf den Raspberry Pi von überall aus innerhalb der Schule. Es war problemlos möglich, über Port 80 auf den Server zuzugreifen. Allerdings wurden alle anderen Ports von der Firewall blockiert, und der Raspberry Pi verfügte zudem über keine statische IP-Adresse.

    Die Lösung bestand zunächst darin, einen der NAS-Server von Herrn Salomon als Reverse Proxy zu nutzen. Diese hatten eine statische IP-Adresse, wodurch der Zugriff auf den Webserver über Port 80 dauerhaft möglich war. So konnte der Webserver stabil erreicht werden.

    Dieses Setup half jedoch nicht, wenn eine Verbindung per SSH erforderlich war. Dafür wurde eine andere Lösung umgesetzt: Obwohl es über den NAS eigentlich nicht vorgesehen war, Ports wie 22 weiterzuleiten, bestand die Möglichkeit, auf die Shell des Geräts zuzugreifen. Da dort bereits iptables installiert war, konnte eine Routing-Regel erstellt werden, die eingehenden Traffic auf Port 222 an den Raspberry Pi auf Port 22 weiterleitet.

    Da beim Neustart des NAS alle Firewall-Regeln zurückgesetzt werden, musste zusätzlich ein Script erstellt werden, das diese Routing-Regel automatisch wiederherstellt.

    #!/bin/sh
echo 1 > /proc/sys/net/ipv4/ip_forward
iptables -t nat -A PREROUTING -p tcp -d 10.1.200.8 --dport 222 -j DNAT --to 172.17.17.131:22
iptables -t nat -A POSTROUTING -p tcp -d 172.17.17.131 --dport 22 -j MASQUERADE

    Implementierung

    Mir war es wichtig, dass man einfach Feedback geben kann und somit Fehler oder Verbesserungsvorschläge unkompliziert übermittelt werden können. Da ich auch nach meiner Assistentenausbildung entweder das Repository an jemand anderen übergeben oder selbst weiter daran arbeiten möchte, ist das besonders sinnvoll.

    Im Allgemeinen ist das Feedback-System ziemlich simpel aufgebaut:
    Name und Nachricht.
    In der Datenbank wird zusätzlich die IP-Adresse des Nutzers gespeichert, allerdings nur aus Sicherheitsgründen und für Rate-Limiting. Die Sicherheit besteht darin, dass man nicht unbegrenzt oft hintereinander Feedback einreichen kann.

    Git:

    Der Server hat ein öffentliches Git-Repository und kann somit modular verändert werden, ohne dass jemand direkt auf dem System arbeiten muss.

    Branches

    Dieses Git-Repository hat mehrere Branches. Zurzeit gibt es den main- und den develop-Branch. Wie die Namen schon sagen, ist der eine der Hauptbranch, auf dem das System normalerweise stabil läuft. Der develop-Branch ist für Updates gedacht, die noch getestet werden müssen und noch nicht vollständig fertig sind. Testweise kann natürlich der Branch auf dem Server auf develop geändert werden, falls dies gewünscht ist. Dies kann jedoch nur der Administrator des Systems. Vielleicht werde ich in Zukunft einen Weg implementieren, um zwischen den Branches zu wechseln, ohne direkt auf das System zugreifen zu müssen.

    Auf dem Server selbst wurde ein Crontab erstellt, welcher jeden Morgen um 07:45 einen Pull vom GitHub-Repository ausführt. Das Skript sollte unter keinen Umständen Fehler enthalten, aber falls doch, würde das System keine regelmäßigen Updates mehr erhalten.

    Zu beachten ist, dass unter keinen Umständen direkt auf dem Server Änderungen an der Website vorgenommen werden sollten, da dies zu Konflikten führen kann.

    Schrank Übersicht

    Die Schrank / Raum Darstellung war zusätzlich zuerst ach eine Herausforderung. Für eine lange Zeit waren auf der Index Seite einfach nur die paar schränke als grüne und braune Vierecke Dargestellt und konnten nichts machen, da ich lange nicht wusste was ich damit anfangen soll. Nach langer Überlegung bin ich zu der isometrischen Sicht gekommen. Man schaut von oben auf die Räume drauf und somit kann man Räume wie den Abstellraum, sowie jeden Schrank übersichtlich darstellen. Außerdem sieht es richtig cool aus! Das ganze ist aus SVG's aufgebaut, welche in Javascript aus gezeichnet werden. Somit muss man nicht zusätzlich jeden Tile selber malen. Jedoch wird somit der Workload der Clients etwas erhöht.

    secure/config.php:

    <?php
mysqli_report(MYSQLI_REPORT_ERROR | MYSQLI_REPORT_STRICT);

class Database
{
    private static $connection = null;

    public static function connect()
    {
        // Verbindung nur einmal erstellen
        if (self::$connection === null) {
            $envPath = "/var/www/secure/.env";
            $env = parse_ini_file($envPath);
            $host = $env["DB_HOST"];
            $user = $env["DB_USER"];
            $pass = $env["DB_PASS"];
            $name = $env["DB_NAME"];
            $conn = new mysqli($host, $user, $pass, $name);
            $conn->set_charset("utf8mb4");
            self::$connection = $conn;
        }
        return self::$connection;
    }
}
