Einleitung

Motivation

In der zweijährigen Assistentenausbildung für Informationsverarbeitung – Technik muss ein vierwöchiges Praktikum nachgewiesen werden, um die Ausbildung abzuschließen. Alternativ darf während der gesamten Ausbildungszeit an einer AG teilgenommen werden, um dasselbe Ergebnis zu erzielen wie durch ein Praktikum.
Zur Auswahl standen die Game-Design-AG und die Maker-AG. Da die Maker-AG interessant aussah und ich somit kein Praktikum absolvieren müsste, habe ich mich für die Maker-AG eingeschrieben.

Nun, ein Jahr später, hat unser Lehrer der AG, Herr Keller, gesagt, dass jeder Schüler, der die Maker-AG als Praktikumsalternative nutzen will, ein Projekt abschließen muss, das der AG langfristig helfen wird. Gesagt, getan...
Die Idee für ein Organisations- und Sortiersystem hatte ich schon etwas länger, wusste aber noch nicht genau, wie ich sie umsetzen würde. Nach weiterer Überlegung und Rücksprache mit dem Lehrer ist schließlich dieses Projekt entstanden. Das Ganze Projekt hat mich noch einmal herausgefordert alles anzuwenden, was ist in der Assistentenausbildung gelernt habe, was sehr viel spaß gemacht hat.

Ziel

Das Ziel des Projektes ist es ein System zu entwickeln, welches Die Gegenstände in den Schränken im Raum U24, U25, und des Hardware Raumes zu Sortieren und Organisieren. Dies wird durch die Erstellung einer Datenbank laufen, welche die Informationen zu dem Gegenstand speichert wie Anzahl; Model/Marke; Standort (Schrank/Raum/Regal); etc. Außerdem wird Jeder Gegenstand eine eigene kleine Dokumentation bekommen welche nochmal in Detail den Gegenstand beschreibt und weiteres.

Anmerkung

Da es zur der Eintragung der ganzen Gegenständen in die Datenbank wenig zu sagen gibt, wird dieser Teil hier eher weniger erwähnt, jedoch wird vieles nochmal in den einzelnen Dokumentationen der Gegenständen Erwähnt werden.

Ich habe mir für dieses Projekt bei vielen Dingen mir viel mühe gegeben um es zu perfektionieren und fände es schätzen, wenn dieses Projekt noch in der Zukunft existiert und weiter genutzt wird.

Ausgangssituation

Das Projekt ging durch viele Überarbeitungen. Eine davon war die Auswahl der Datenbank, welche genutzt werden würde um alle daten der Gegenstände zu speichern. Herr Keller schlug mir MongoDB, wovon ich davor noch nicht gehört hatte. MongoDB wäre in diesem Fall sogar etwas besser gewesen, da man es einfacher hätte integrieren können. Ein Problem nur war die Installation. Da der Raspberry Pi ein ARM64-Produkt war und MongoDB hauptsächlich auf x86-64 läuft, waren die wenigen Versionen, die für ARM erstellt wurden, entweder veraltet, inkompatibel oder einfach instabil. Das war etwas frustrierend, und nach einiger Zeit habe ich einfach aufgegeben und statt MongoDB MariaDB installiert, welches auf SQL basiert.

Design


Der Prozess läuft so ab, dass sobald ein Nutzer die Website aufruft, sendet es einen Request an den Server um alle HTML Seiten zu bekommen. Diese HTML Seiten verlinken zu den JavaScript und CSS Dateien, welche auch Requested werden. In den JavaScript Dateien ist eine Verlinkung zu einer PHP Datei welche dann auch auf die Seite geladen wird. in der PHP Datei ist Code, welcher eine Verbindung mit einer MariaDB Datenbank auf dem Raspberry Pi herstellt und von dort die gewünschten Daten holt.

Datenbank:
Die Datenbank hatte sehr viele veränderungen über die Projektzeit und hat viele änderungen bekommen:
Um Die Datenbank besser zu verstehen und zu visualisieren, habe ich ein Entity Relationship Modell erstellt:

Legende:

  • PK – Primary Key Eindeutige ID für jeden Eintrag in dieser Tabelle. Kein Wert darf doppelt vorkommen oder leer sein.
  • FK – Foreign Key Fremdschlüssel. Verweist auf die ID einer anderen Tabelle und stellt sicher, dass nur Werte eingetragen werden können die dort auch wirklich existieren.
  • categories.parent_id (Self-Reference) Zeigt auf eine andere Zeile in derselben Tabelle. Damit lassen sich Kategorien beliebig tief verschachteln, z.B. Hardware → Computer → Laptop. NULL bedeutet: oberste Ebene, kein Elternteil.
  • specs (Key-Value) Statt für jeden möglichen Spec eine eigene Spalte in items anzulegen, speichert diese Tabelle beliebige Eigenschaften als Schlüssel-Wert-Paare. Ein Laptop bekommt "Prozessor / i5", ein Hammer bekommt "Gewicht / 800g" — ohne dass die Datenbankstruktur geändert werden muss.
  • item_tags (Pivot-Tabelle) Verbindet items und tags in einer Viele-zu-Viele-Beziehung. Ein Item kann mehrere Tags haben, ein Tag kann mehreren Items zugewiesen sein. Die Tabelle selbst hat keine eigenen Daten, nur die zwei Fremdschlüssel.
  • changelog Protokolliert jede Änderung an einem Item. Welches Feld wurde geändert, von welchem Wert, auf welchen Wert, wann und von wem. Damit lässt sich der komplette Verlauf eines Eintrags nachvollziehen.
