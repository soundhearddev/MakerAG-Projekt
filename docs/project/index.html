Einleitung

Motivation

In der zweijährigen Assistentenausbildung für Informationsverarbeitung – Technik musste ein vierwöchiges Praktikum nachgewiesen werden, um die Ausbildung abzuschließen. Alternativ darf während der gesamten Ausbildungszeit an einer AG teilgenommen werden, um dasselbe Ergebnis zu erzielen wie durch ein Praktikum.
Zur Auswahl standen die Game-Design-AG und die Maker-AG. Da die Maker-AG interessant aussah und ich somit kein Praktikum absolvieren müsste, habe ich mich für die Maker-AG eingeschrieben.

In meinem zweiten Lehrjahr, hat unser Lehrer der AG, Herr Keller, gesagt, dass jeder Schüler, der die Maker-AG als Praktikumsalternative nutzen will, ein Projekt abschließen muss, das der AG langfristig helfen kann.
Die Idee für ein Organisations- und Sortiersystem hatte ich schon etwas länger, wusste aber noch nicht genau, wie ich sie umsetzen würde. Nach weiterer Überlegung und Rücksprache mit dem Lehrer ist schließlich dieses Projekt entstanden. Das ganze Projekt hat mich noch einmal herausgefordert, alles anzuwenden, was ich in der Assistentenausbildung gelernt habe, was sehr viel Spaß gemacht hat.

Ziel

Das Ziel des Projektes ist es, ein System zu entwickeln, welches die Gegenstände in den Schränken im Raum U24, U25 und des Hardware-Raumes sortiert und organisiert. Dies wird durch die Erstellung einer Datenbank erfolgen, welche die Informationen zu den Gegenständen speichert, wie Anzahl, Modell/Marke, Standort (Schrank/Raum/Regal) etc. Außerdem wird jeder Gegenstand eine eigene kleine Dokumentation bekommen, welche noch einmal im Detail den Gegenstand beschreibt und Weiteres.

Ausgangssituation

Das Projekt durchlief im Laufe der Entwicklung mehrere Überarbeitungen. Eine davon betraf die Wahl der Datenbank, mit der die Informationen zu den Gegenständen gespeichert werden sollten. Herr Keller schlug dafür MongoDB vor, womit ich zuvor noch keine Erfahrung hatte.

MongoDB hätte sich in diesem Fall sogar besser geeignet, da sich die Datenbank einfacher integrieren ließ. Problematisch war jedoch die Installation auf dem Raspberry Pi. Da dieser auf einer ARM64-Architektur basiert und MongoDB hauptsächlich für x86-64 entwickelt wird, waren die wenigen verfügbaren ARM-Versionen entweder veraltet, inkompatibel oder instabil.

Nach mehreren erfolglosen Versuchen entschied ich mich schließlich dazu, stattdessen MariaDB zu verwenden, da ich bereits Erfahrung mit SQL-basierten Datenbanken hatte.

Soll-Zustand

Angestrebt wird eine funktionierende Datenbank sowie eine lauffähige Website mit funktionierendem Backend bzw. API. Darüber hinaus sollen alle Gegenstände in die Datenbank eingetragen und entsprechend dokumentiert sein. Ergänzend dazu ist eine Integration für externe Beiträge über GitHub vorgesehen, sowie eine vollständige Dokumentation des Projektes und weiterer relevanter Aspekte.

Design


Datenbank:
Die Datenbank hat sich über die Projektzeit stark verändert und viele Anpassungen bekommen. Um die Datenbank besser zu verstehen und zu visualisieren, ist hier ein Entity-Relationship-Modell:

Legende

categories.parent_id – Self-Reference

Zeigt auf eine andere Zeile in derselben Tabelle. Damit lassen sich Kategorien beliebig tief verschachteln, z.B. Hardware → Computer → Laptop. NULL bedeutet: oberste Ebene, kein Elternteil.
[!info] specs – Key-Value
Statt für jeden möglichen Spec eine eigene Spalte in items anzulegen, speichert diese Tabelle beliebige Eigenschaften als Schlüssel-Wert-Paare. Ein Laptop bekommt "Prozessor / i5", ein Hammer bekommt "Gewicht / 800g", ohne dass die Datenbankstruktur geändert werden muss.

item_tags – Pivot-Tabelle

Verbindet Items und Tags in einer Viele-zu-Viele-Beziehung. Ein Item kann mehrere Tags haben, ein Tag kann mehreren Items zugewiesen sein. Die Tabelle selbst hat keine eigenen Daten, nur die zwei Fremdschlüssel.

logs

Protokolliert jede Änderung von einem Gegenstand, von welchem Wert auf welchen, wann und von wem. Damit lässt sich der komplette Verlauf eines Eintrags nachvollziehen.

feedback

Sehr simpel gehaltene Tabelle mit nur Name, Nachricht und Timestamp. Bewusst so minimal gehalten um kein Benutzersystem implementieren zu müssen.

Administration

Da die Administrationsseite ausschließlich lokal auf dem Raspberry Pi erreichbar ist, wird für den Zugriff ein SSH-Tunnel genutzt. Dies hat den Vorteil, dass der gesamte Traffic über eine verschlüsselte SSH-Verbindung läuft, ohne dass HTTPS extra konfiguriert werden muss.

Netzwerk-Setup

Weil der Raspberry Pi während der Projektlaufzeit über keine statische IP-Adresse verfügte und die Schulfirewall, außer für Geräte im selben Subnetz, alle Ports außer Port 80 blockiert, musste eine Lösung gefunden werden, um den Server dauerhaft erreichbar zu machen, da für eine SSH Verbindung port 22 verfügbar sein muss[1].

Für den HTTP-Zugriff wird ein NAS-Server als Reverse Proxy genutzt, der über eine statische IP-Adresse verfügt. Dadurch ist der Webserver über Port 80 dauerhaft erreichbar.
Für den SSH-Zugriff wurde auf demselben NAS eine iptables-Regel eingerichtet, die eingehenden Traffic auf Port 222 an Port 22 des Raspberry Pi weiterleitet:

echo 1 > /proc/sys/net/ipv4/ip_forward
iptables -t nat -A PREROUTING -p tcp -d 10.1.200.8 --dport 222 -j DNAT --to 172.17.17.131:22
iptables -t nat -A POSTROUTING -p tcp -d 172.17.17.131 --dport 22 -j MASQUERADE

Da beim Neustart des NAS alle iptables-Regeln zurückgesetzt werden und somit über den NAS aus keine Verbindung mehr möglich ist, können diese befehle benutzt werden, um routing Tabellen wieder zu aktivieren. dies benötigt jedoch einen Zugriff au einen admin account des QNAS Servers.

SSH-Tunnel / Verbindung

SSH Local Port Forwarding ermöglicht es, einen lokalen Port von dem eigenen Rechner mit einem Port auf dem Zielserver zu verbinden. Um so eine Art einer Verbindung zu verdeutlichen, ist hier eine kleine Grafik:
Es gibt zwei Webseiten: eine öffentliche Seite, die von jedem Nutzer besucht werden kann, und eine private Seite, die nur vom localhost aus erreichbar ist.

Der SSH Befehl für so eine Verbindung sieht so aus:

ssh -L 8080:127.0.0.1:80 -N user@10.1.218.18
  • -L 8080:127.0.0.1:80 — leitet den lokalen Port 8080 an Port 80 auf dem Raspberry Pi weiter
  • -N — öffnet keine Shell, hält nur den Tunnel offen

Wenn alles problemlos abgelaufen ist, wird kein Output angezeigt, was etwas verwirrend sein kann, da man keine Rückmeldung über den Erfolg des Vorgangs erhält.

Zugriff auf die Admin-Seite

Sobald der Tunnel steht, ist die Seite unter localhost:8080 erreichbar. Das Terminal muss dabei offen bleiben.

Der Apache VirtualHost ist so konfiguriert, dass die private Seite ausschließlich über den localhost erreichbar ist:

<VirtualHost 127.0.0.1:80>
	ServerName localhost
	DocumentRoot /var/www/private/ 
  
	<Directory /var/www/private/>
		AllowOverride All
		Require local 
	</Directory>
</VirtualHost>

Sicherheitskonzept

Da die Sicherheit der Administration eine hohe Priorität hatte, wurde versucht, die maximale Sicherheit herauszuholen. Eines der größten Probleme war das unverschlüsselte HTTP. Da HTTPS ohne Zertifikate schwierig zu konfigurieren ist, musste ein Umweg gefunden werden.

Die Lösung war SSH-Tunneling: Der gesamte Traffic läuft verschlüsselt durch den SSH-Tunnel, wodurch HTTPS nicht benötigt wird. Intern sieht der Webserver dabei lediglich eine Verbindung vom localhost.

Für den SSH-Zugriff wurden dedizierte Proxy-User eingerichtet. Public Keys zu verwenden funktioniert schlecht für Schulrechner, auf denen Daten häufig nicht persistent sind. Deshalb wurde passwortbasierte Authentifizierung gewählt, wobei bei jeder Anmeldung das Passwort des jeweiligen Benutzers abgefragt wird.

Als zusätzliche Sicherheitsmaßnahme haben diese Proxy-User keinen Shell-Zugriff und können damit ausschließlich für SSH-Tunneling genutzt werden.

phpMyAdmin läuft ebenfalls unter dieser privaten Verbindung und ist nur über localhost:8080/phpmyadmin erreichbar. Hierfür wird das Admin passwort benötigt.

Implementierung

Git:

Der Quellcode ist in einem öffentlichen GitHub-Repository verfügbar: hier

Änderungen können dadurch eingereicht werden, ohne direkten Zugriff auf das System zu benötigen.

Branches

Branch Zweck
main Stabiler Produktivbetrieb
develop Neue Features, noch in Entwicklung
assets nur für Sicherung und Bestandhaltung der Gegenstände

Der Server zieht jeden Morgen um 07:45 automatisch den aktuellen Stand vom Repository.
45 7 * * * /var/script/pull.sh

Kurz vor Beendigung des Projektes ist mir aufgefallen, dass der Server aktiv in den docs/ Ordner schreibt, wenn es neue Gegnstände erstellt. Somit könnten potenzielle Git-Konflikte oder Datenverlust beim täglichen Pull auftauchen.

Das ursprüngliche Pull-Script nutzte git reset --hard origin/main kombiniert mit git clean -fd. Das bedeutet: Origin hat immer Recht, und alle ungetrackten Dateien werden gelöscht. Da der Server Bilder und PDFs hochlädt die Git nicht kennt, würden diese bei jedem Pull unwiderruflich gelöscht werden.

Die Lösung hierfür war ein separater assets Branch, der ausschließlich den docs/items/ Ordner tracked. Der branch wird nie von außen angefasst, und der Server pusht nie auf main oder develop. Dadurch sind die zwei Verantwortlichkeiten klar getrennt:

  • main / develop → nur Code, nie docs/items/
  • assets → nur docs/items/, nie Code

Das Pull-Script macht folgendes:

  1. Aktuellen Stand von docs/items/ als Backup sichern
  2. Neue Uploads auf assets pushen und auf Origin sichern
  3. Code von main holen via git reset --hard origin/main
  4. docs/items/ von assets wiederherstellen
  5. Backup aufräumen

Dadurch gehen nie Uploads verloren, es entstehen keine Merge-Konflikte, und der Server sowie die Entwicklung arbeiten völlig unabhängig voneinander.

Schrank Übersicht

Die Schrank- und Raumdarstellung stellte sich als eine der größeren Herausforderungen heraus. In einer frühen Version waren die Schränke lediglich als einfarbige Rechtecke dargestellt, ohne jegliche Interaktion oder klare Struktur.

Nach längerer Überlegung fiel die Entscheidung auf eine isometrische Ansicht von oben, die es ermöglicht, Räume wie den Abstellraum sowie einzelne Schränke übersichtlich darzustellen. Die gesamte Darstellung wird per JavaScript als SVG gerendert, wodurch einzelne Tiles nicht manuell gezeichnet werden müssen. Dies erhöht jedoch den Rechenaufwand auf Client-Seite minimal.

Feedback-System

Mir war es wichtig, dass man einfach Feedback geben kann und somit Fehler oder Verbesserungsvorschläge unkompliziert übermittelt werden können. Da ich auch nach meiner Assistentenausbildung entweder das Repository an jemand anderen übergeben oder selbst weiter daran arbeiten möchte, ist das besonders sinnvoll.

Im Allgemeinen ist das Feedback-System ziemlich simpel aufgebaut:
Name und Nachricht.
In der Datenbank wird zusätzlich die IP-Adresse des Nutzers gespeichert, allerdings nur aus Sicherheitsgründen und für Rate-Limiting. Die Sicherheit besteht darin, dass man nicht unbegrenzt oft hintereinander Feedback einreichen kann.

Gegenstanddokumentation

Die gegenstanddokumention für jeden Gegenstand ist eigentlich im Hintergrund nur eine Leere html Seite, welche dann beim laden die Daten von der id des Gegenstandes nimmt und diese dann auf der website anzeigt.

In der frühen Entwicklungsphase wollte ich jeden Gegenstand manuell beschriften und beschreiben, was rückblickend ziemlich ambitioniert klingt. Mir wurde jedoch schnell klar, dass es SEHR viele Objekte in den Schränken gibt. Zusätzlich fiel mir auf, dass zahlreiche Gegenstände unbrauchbar, unvollständig oder schlichtweg Müll waren. Dadurch entstand letztlich das Hauptproblem: zu entscheiden, welche Objekte dokumentiert werden sollen und welche nicht.

Die Gegenstandsdokumentation war ein darauffolgender Ansatz, bei dem die Informationseintragung der Objekte automatisiert werden sollte. Eine erste Idee war, ein Computer-Vision-Modell einzusetzen, das die Gegenstände klassifizieren könnte. Dies war jedoch aufgrund des zuvor beschriebenen Problems nicht praktikabel [2].

Schlussendlich habe ich die „Automatisierung“ als Hauptprinzip gewählt. Das bedeutet, dass alle Daten der Gegenstände in der Datenbank gespeichert sind, und daraufhin gut auf eine Seite geladen werden kann.

Ergebnis

Das Endergebnis dieses Projekts ist eine gute Grundlage für die Sortierung und Dokumentation der Gegenstände. Leider konnten nur wenige Gegenstände vollständig eingetragen werden, und viele Einträge sind noch unvollständig. Die weitere Erfassung und Vervollständigung der Daten liegt daher nun in den Händen anderer.
Ich bin etwas stolz auf den Inhalt dieses Projekts, da daraus letztlich ein funktionierendes und erweiterbares System entstanden ist.

Einstellungen

In den Einstellungen habe ich ein paar experimentelle Features hinzugefügt, welche einfach nur aus Spaß dort sind. Hier werde ich kurz erklären, was diese sind und wie diese genau funktionieren:

Das erste Feature ist der Game-of-Life-Modus. Dieser füllt, wenn aktiviert, den kompletten Bildschirm mit Conways Spiel des Lebens. Ich werde nicht erklären, wie Conways Spiel des Lebens genau funktioniert, nur dass es ein faszinierendes Thema ist. Der Code selbst ist technisch unspektakulär: JavaScript erstellt ein Overlay über den Bildschirm, auf dem viele Zellen simuliert werden, die miteinander interagieren. Die Implementierung ist dabei sehr effizient und bringt die Seite in der Regel nicht zum Laggen.

Das nächste Feature ist der Vim-Modus. Ich habe versucht, so viele Befehle wie möglich umzusetzen, ohne größere Änderungen am bestehenden Code vorzunehmen, und kann bestätigen, dass die Nutzung des Vim-Modus™ die Effizienz spürbar steigert. Für eine Liste an Befehlen kann der :help-Befehl genutzt werden. Hauptsächlich führen die Befehle einfach Funktionen aus den Settings aus, aber es ermöglicht sehr gute Navigationsfunktionen.

Erklärung

Ich bin ganz ehrlich: Ich könnte jetzt noch jeden Prozess im Detail erklären, aber darauf habe ich ehrlich gesagt keine Lust. Wenn Fragen zum Code oder zu anderen serverseitigen Komponenten auftauchen, kann man mich einfach persönlich kontaktieren.

Fazit

Dieses Projekt hat mit in meinem zweiten Lehrjahr begleitet und es hat sehr viel Spaß gemacht die einzelnen ideen und Funktionen wirklich zu implentieren. Ich muss sagen, dass es für die größe nicht besonders herrausfordernt war, es jedoch trotzallem eine gute erfahrung war, bei der ich vieles neues gelernt habe.

Meiner Meinung nach ist der Grundbaustein des Projektes und 90% aller Sachen vollendet, was mich mit glücklich macht.

Ausblick

Da ich in den nächsten zweieinhalb Jahren weiterhin an dieser Schule bin, werde ich das Projekt gelegentlich weiterentwickeln und bei Bedarf Updates veröffentlichen. Außerdem stehe ich weiterhin für Fragen oder Feedback zur Verfügung.

Geplant sind noch einige Verbesserungen und Erweiterungen, insbesondere in den Bereichen Funktionalität und Benutzerfreundlichkeit, wie ein bisschen bessere Übersicht und Kontrolle den Gegenständen und eine Überarbeitung der Index Seite. Zusätzlich will ich das feedback system erweitern und für Administration übersichtlicher machen. Unabhängig davon bin ich mit dem aktuellen Stand des Projekts bereits zufrieden, da die wichtigsten Ziele erreicht wurden.

Mein Ziel ist es, dass das System in Zukunft eine stabile und nutzbare Plattform für andere darstellt, um Informationen über das derzeitige Sortiment zu finden und insbesondere Ordnung in den Schränken im Raum U25 zu schaffen.

Für die weitere Zukunft, sofern dieses Projekt bis dahin nicht bereits verworfen wurde, werde ich wahrscheinlich das Repository an jemand anderen weitergeben, der es dann künftig weiterführen und Updates veröffentlichen kann.

Anhang

secure/config.php:

<?php
mysqli_report(MYSQLI_REPORT_ERROR | MYSQLI_REPORT_STRICT);

class Database
{
    private static $connection = null;

    public static function connect()
    {
        // Verbindung nur einmal erstellen
        if (self::$connection === null) {
            $envPath = "/var/www/secure/.env";
            $env = parse_ini_file($envPath);
            $host = $env["DB_HOST"];
            $user = $env["DB_USER"];
            $pass = $env["DB_PASS"];
            $name = $env["DB_NAME"];
            $conn = new mysqli($host, $user, $pass, $name);
            $conn->set_charset("utf8mb4");
            self::$connection = $conn;
        }
        return self::$connection;
    }
}
